# CLAUDE.md

Guidance for AI coding agents working in this repository.

## Project

SimpleScripture is a GPL'd iOS Bible-study app, forked from PocketSword at `bitbucket.org/niccarter/pocketsword`. It ships CrossWire SWORD module *content* baked into a bundled SQLite store; there is no SWORD engine, C++ or Objective-C at runtime.

- **Pure Swift.** `Classes/` is Swift files plus one header, `globals.h` (enums + constants, imported by both bridging headers). No vendored code, no CocoaPods/SPM.
- **SwiftUI UI.** `@main SimpleScriptureApp` with a four-workspace `TabView` (Read / Search / Library / Settings). No XIBs; only `LaunchScreen.storyboard`. No WebKit: the reader is a native `ScrollView` + `LazyVStack` over `AttributedString`. UIKit survives only as leaf values plus a `@UIApplicationDelegateAdaptor` for `BGTaskScheduler` registration and the orientation hook.
- Old implementations (SWORD engine, Obj-C++ bridge, `tools/swordbake`, WebView reader) are in git history at `fa09511^`. Do not resurrect them.

## Build / run

- Open `SimpleScripture.xcodeproj` and build the shared `SimpleScripture` scheme. No workspace, no package step.
- CLI: `xcodebuild -project SimpleScripture.xcodeproj -scheme SimpleScripture -configuration Debug -sdk iphonesimulator build`, with `CODE_SIGNING_ALLOWED=NO` if there is no dev team. Prefer Xcode MCP; check `xcode-select -p` and installed destinations before using the CLI. Regular Xcode currently provides the iOS 27 SDK.
- A clean build should show **`CompileC` 0**. Any `CompileC` means non-Swift sources came back into the target — a regression.
- Configurations `Debug` / `Release` / `Distribution` all build `SimpleScripture.app` with bundle ID `org.timsam.SimpleScripture` and team `7SZUJ26BQ2`. Debug/Release use empty `SimpleScripture.entitlements` so Personal Team device signing works; history and bookmarks remain local. Distribution uses `SimpleScripture-Distribution.entitlements` for iCloud key-value storage and requires a team that supports iCloud before signing. The Swift module, project, app target and shared scheme use `SimpleScripture`; the scheme archives with `Distribution`. This is a separate app identity; old PocketSword containers are not migrated. Those three configurations share one local installation.
- A second shared scheme, `SimpleScriptureDev`, builds `Debug-Dev` / `Release-Dev`: the same app as **`org.timsam.SimpleScripture.dev`** ("SimpleScripture Dev"), so it installs beside the App Store build with its own container, and registers `sword-dev://` instead of `sword://` (`SIMPLESCRIPTURE_URL_SCHEME`, substituted into `misc/icon/Info.plist`; `URLRouter` accepts `sword` plus whatever the bundle registers, in any letter case). Check which scheme is active before resolving a container or driving a URL.
- `IPHONEOS_DEPLOYMENT_TARGET = 27.0` on all 3 targets × 5 configs; universal. `SWIFT_VERSION = 5.0`, `SWIFT_STRICT_CONCURRENCY = minimal`. No prefix header.
- zlib comes from the SDK's Clang module (`import zlib` in `PSContentStore`); no build setting needed.

## Tests

Two bundles:

- **`SimpleScriptureTests`** (app-hosted, `@testable import SimpleScripture`), sources in `Classes/*Tests.swift`. Expected result: **0 failures, 3 skipped** (236 tests at last count). The 3 skips are env-gated: two `PSREF_EXHAUSTIVE` tests and `PSDOC_EXHAUSTIVE`'s `testNativeDocumentMatchesHTMLForEveryChapter` (all 1,189 chapters × 2 modules × 2 option endpoints, ~30 s — run it when touching either chapter emitter). The same switch widens `testTheReadersWordsAreTheWordsTheSearchMatched` from the sample chapters to every KJV chapter (~8 s in all); that one never skips.
  - **The host app's own reader runs beside the tests, on the same `UserDefaults.standard`.** It saves the four reader position keys on main-actor turns of its own, so an `async` test that awaits between a write to one of those keys and the assertion on it can read the host's value (measured 2026-11-11, iOS 27.2: a reader test failed once in five class runs reading `"1144"` / `"9"`, which nothing in it writes; with a redisplay posted on the shared notification centre and the await held open, the host saved over the keys 5 runs in 5). It is rare unprovoked — a watch on the keys saw no host save inside an await in 6 seeded runs — which is what makes it look like a flake. In a reader test that awaits, read a position key on the turn it is written: assert before the `await`, or write the key again after it, immediately before the synchronous call whose effect on the key is being checked (`sizeChange`'s doc comment in `AppStateStoresTests` has the rule). `lastRef` is not at risk: the host rewrites it only with the value it has just read.
- **`SimpleScriptureUITests`** (`Tests/SimpleScriptureUITests.swift`): 28 XCUITests over the four workspaces. Its Target Application is `SimpleScripture`. iPhone-only: `selectWorkspace` matches `app.tabBars`, which an iPad does not have, so the 18 tests that change workspace fail there at "Missing workspace …" for whichever tab they tap first; the other 10 never touch the tab bar and have not been run on an iPad. Expected result on a headless simulator: **0 failures, 1 skipped** (`testScrollingSearchResultsDismissesTheKeyboard`, below; a full run of all 28 takes about 20 minutes — measured 2026-11-11, iOS 27.2).
  - **A simulator booted by `simctl` with no Simulator window does not draw the software keyboard** (measured 2026-11-11, iOS 27.2; the per-device `ConnectHardwareKeyboard = false` preference made no difference). The `Keyboard` element is in the hierarchy from the moment a field is tapped, parked below the screen (`{{0, 918}, {402, 226}}` on an 874-point screen), so `app.keyboards.firstMatch.exists` proves nothing. Judge a keyboard by its frame (`waitForKeyboard(onScreen:)`) and what the app decides by the field's keyboard focus (`waitForKeyboardFocus`). With none drawn a scroll of the search results leaves the field focused, so `testScrollingSearchResultsDismissesTheKeyboard` **skips** there — its assertions have not yet run on any simulator — and `testOpeningASearchResultWithTheKeyboardUpLandsOnItsVerse` passes without exercising what it guards: its precondition is still `exists`, and with no keyboard on screen the reader is never laid out at the keyboard's height.
  - **`testFlowingReaderTracksTheVisibleVerseWithinAParagraph` holds its drag still before lifting, on purpose.** It brings its own chapter and layout (a relaunch with Verse Per Line off at 18 pt, Genesis 1 through the reference picker), so it passes alone or after any test. A drag let go while moving coasts: 149 pt of travel scrolled 332 pt (measured 2026-11-11, iOS 27.2), past the foot of Genesis 1's first paragraph (304 pt), where the next row's first verse changes the title with no inline tracker at all. Held, the reader moves 184–190 pt and the test checks that the verse in the title has text on the top line. Don't swap the drag for a swipe or drop the hold.
  - **`selectWorkspace("Read")` as a test's first step is a reselect.** The app always launches on Read, and reselecting the selected tab is the system's scroll-to-top: the reader goes to the top of the chapter and persists that, straight after a launch that restored a position deep in a chapter included: verse 1 at (16, 116) in 14 tries of 14 (measured 2026-11-11, iOS 27.2). With the restored offset left in `ScrollPosition` it lands wrong — short of the top in 3 tries of 7, against the screen edge in 1 of 7, where the trace has the offset applied raw as the scroll to the top starts (see Native reader). Pick a chapter before asserting a position.
  - **A UI run leaves the font on Georgia, the Library section on Bookmarks, Verse Per Line on and the font size as it found it**: the tests that change them choose the default again at their end, and the size is put back in a teardown block. A test that fails part-way leaves its change behind (the size excepted), and the reader's place, history rows and `lastDictionary` stay where the tests put them (`testStrongsLinkInAPsalmTitleOpensItsLexiconEntry` stops in Psalms 3).
  - `XCUIDevice.shared.orientation` turns a headless simulator, and frames come back in the turned space (iPhone 18 Pro in landscape: 874×402, navigation bar ending at y 78, side safe-area inset 62). `testRotatingTheReaderKeepsTheVerseBeingRead` puts portrait back in a teardown block and passes `-rotationLockedPosition 0`: Rotation Lock is a saved setting, and a locked app does not turn.
  - Waits are coarse: `waitForExistence` and a predicate wait first poll after 1 s and a tap takes about 2 s, so a trip through the reference picker costs 8 s, `selectWorkspace` 3.4 s and a relaunch 4–5 s (measured 2026-11-11, iOS 27.2).
  - `testBookmarkFolderCrudAndReordering`'s long-press reorder is timing-sensitive: it failed once in a full run while a second `xcodebuild` was building alongside, and passed alone. Don't build in parallel with a UI test run.

Rules:

- **Fixtures in `Tests/Fixtures/` were captured from the live SWORD engine, which is gone.** They cannot be regenerated. A red fixture test is a real behaviour change — fix the code, never recapture or "fix" the test. Key fixtures: chapter bodies at both option endpoints, lexicon entries, `versification-KJV-oracle.txt` (the whole versification gate), `search-index-KJV.digest` (all 31,102 FTS rows, hashed), `chapter-loop-counters.tsv` (`entryCount` per chapter). `strongsPad-prefixed-key-bug.txt` is a historical record, not an oracle.
- **`PersistedFormatTests` locks byte-exact persisted formats** (history / bookmark / search-history serialization, the per-module pref-key format), quirks included. A red test there means you will corrupt user data.
- **`PSSearchIndexParityTests`** runs a real index build (tens of seconds) and compares every row against the digest. It stays in the default suite because the failure it guards is silent: search results just go missing.
- **Check the skip count, not just the pass count.** A skipped test reports green having asserted nothing. One XCUITest can skip: `testScrollingSearchResultsDismissesTheKeyboard`, when no software keyboard is on screen (above). The three lexicon XCUITests (`testStrongsLinkOpensItsLexiconEntry`, `testLexiconCrossLinkNavigatesWithinThePopup`, `testStrongsLinkInAPsalmTitleOpensItsLexiconEntry`) turn Strong's numbers on by launch argument (`-strongsPreference_KJV YES`), so they need nothing from the container — a freshly erased simulator and an `xcodebuild` clone have the numbers off — and fail, not skip, when a marker or a cross-link is missing.
- **Env vars in a test run.** From the CLI, prefix the variable with `TEST_RUNNER_`: `xcodebuild` passes it to the test runner with the prefix removed (`TEST_RUNNER_PSDOC_EXHAUSTIVE=1 TEST_RUNNER_PSREF_EXHAUSTIVE=1 xcodebuild test …` runs all three env-gated tiers of the app-hosted unit bundle: 0 skipped, verified). From Xcode or the MCP tools — `RunAllTests` / `RunSomeTests` have no env parameter — the only way is a temporary `<EnvironmentVariables>` block in the shared scheme's `TestAction` **plus** `shouldUseLaunchSchemeArgsEnv = "NO"`. The scheme is checked in — back it up and restore it.
- From the CLI, `-destination 'platform=iOS Simulator,id=<UUID>'` works where `name=...` may not. `xcodebuild` runs the tests on **clones** of that simulator ("Clone 1 of iPhone 18 Pro") unless you pass `-parallel-testing-enabled NO` — and a clone is a fresh install, so a container you seeded is not the one under test.
- **If every XCUITest fails in `setUp` with "Timed out while evaluating UI query", or Xcode says it `Could not attach to pid`, the harness is wedged, not your change.** A crashed Xcode leaves a `testmanagerd` inside the simulator runtime holding the debug slot. `kill -9` the one whose path contains `…SimulatorRuntime…/RuntimeRoot/usr/libexec/testmanagerd` (not the host's `/usr/libexec/testmanagerd`) and reboot the device. Confirm attribution by stashing your change and re-running.

## Driving the app on the simulator (Xcode MCP)

- Session: `DeviceInteractionStartWorkspaceSession` → `DeviceInteractionInstallAndRun` → `DeviceInteractionSynthesize` (repeat) → `DeviceInteractionEndSession`. Use the *Workspace* variant (the plain one cannot install). Always end the session.
- Xcode MCP calls take a `workspaceIdentifier` from `XcodeListWorkspaces` (the project is listed once per open window).
- `interactionCommand` syntax is in the `device-interaction` skill (`~/.claude/skills/device-interaction/`; re-export with `xcrun agent skills export <dir>`). Common: `t <x> <y>` tap, `d <x> <y>` double tap, `t <x1> <y1> f <x2> <y2>` swipe, `w <dur>` wait, `b h` home, `sender keyboard kbd <text>` (must be last; `\u{000A}` is Return). Omit the command to just capture state.
- **Use the hierarchy file for coordinates**, not the screenshot: each element has a `hitPoint`. Every verse is a `StaticText` and every Strong's / morph / footnote / verse-menu target is a `Link` whose identifier is its `pslink://` URL (e.g. `pslink://strongs/Hebrew/0430`).
- The reader `ScrollView` has identifier `reading.chapter-content`. **Both panes carry it** (the inactive one sits at `opacity(0)`), so XCUITests must use `.firstMatch` — and `.firstMatch` is not always the pane on screen: back in the Bible after a visit to the commentary it was the hidden commentary pane (measured, iOS 27.2). The hidden pane's `.accessibilityHidden` reaches XCUITest: its scroll view is in the hierarchy with no text and no links under it, so a text or link query cannot match it. Use `.firstMatch` on it for the frame and for gestures only; find rows app-wide (a `pslink://versemenu/…` link exists only in the Bible pane), or under the identifier's whole query — `app.scrollViews.matching(identifier: "reading.chapter-content").staticTexts`, as `testChapterOpensOnVerseOneWithHeadingsOff` does — where only the showing pane has any.
- SwiftUI identifiers must be checked against a real dump: `Tab`'s `accessibilityIdentifier` never reaches the tab-bar button (match tabs by label), and a menu row exposes its label, not its identifier.
- The app always launches on the Read tab and restores the reader's scroll position; capture before assuming where it starts.
- Sheets animate in: `w 2.0` before capturing. A sheet leaves the page under it in the hierarchy (the `Preferences` bar exists the whole time the Font sheet is up), and `isHittable` is true of a list row sitting under the sheet's bar (measured, iOS 27.2). Judge by frames.
- **The reference picker is one navigation stack whose bar takes the page's title**: `Select Book`, then the book (`Genesis`), then book and chapter (`Genesis 3`). The verse page's bar going is what says the picker has closed. The book list is lazy and opens centred on the reader's own book, so the row of a distant book is not in the hierarchy (measured, iOS 27.2: no `reference.book.Gen` with the reader in Psalms 3) and a test must scroll to its book — the XCUITest helpers `selectGenesisChapter` / `selectChapter(_:verse:ofBook:named:)` do (Genesis is 1 swipe from Psalms 3, 4 from Revelation 22).
- **To check an animation, record it.** A capture is taken after the UI settles, so it cannot show one. Run `xcrun simctl io <device> recordVideo --codec h264 --force <file>.mov` in the background around the `Synthesize`, stop it with `SIGINT`, and pull the frames with `ffmpeg -i <file>.mov -fps_mode passthrough …`. The recording has a frame only when the screen changes, so read the frame timestamps (`showinfo`) instead of assuming a rate: a gap is the screen standing still.
- Per-run env vars for an **app** run: `InstallAndRun`'s `environmentVariables` / `commandLineArguments` (`$(inherited)` keeps the scheme's own).
- **A default passed as a launch argument (`-lastRef "Genesis 1"`) shadows every write the app makes to that key for the whole run.** Fine for a read-once seed or a display setting; wrong for anything the run changes — page a chapter under `-lastRef` and the text moves on while the title, the chevron enablement and the next page all still read the argument. The argument itself writes nothing, but the app's shadowed writes still reach the container and the next run starts from them: a run under `-lastRef "Psalms 3"` left the container on Psalms 3, and an offset saved under `-fontSizePreference 18` names another verse at the container's own size (measured 2026-11-11, iOS 27.2). The XCUITest helper `openGenesis1WithStrongsNumbers` seeds `-lastRef` on purpose — its tests open a popup and go nowhere — because with Strong's numbers on a long flowing chapter slows every element query: 2.2 s in Genesis 3 against 0.35 s (measured).
- **To seed a key the run changes, edit the app container plist**: `plutil -replace strongsPreference_KJV -bool YES <container>/Library/Preferences/org.timsam.SimpleScripture.plist` (`simctl spawn defaults write` does not take). On an already-launched container, also flush the simulator's `cfprefsd` or the app gets the cached value: `xcrun simctl spawn <device> launchctl kill SIGKILL system/com.apple.cfprefsd.xpc.daemon`. Cheap sanity check: seed `fontSizePreference` to 30 and confirm the text visibly changes. Reading the plist back after `simctl terminate` can be stale — `cfprefsd` writes late (measured 2026-11-11, iOS 27.2: a read 1–2 s after returned the keys from before the last write in 2 cycles of 3; how long is enough is not established). To check a persisted position, launch again without touching the file and look.
- `StartWorkspaceSession` / `InstallAndRun` drive the Xcode window's own scheme and run destination. If the owner is working in Xcode (active destination is a physical device), build from the CLI with a private `-derivedDataPath` and drive the simulator with `simctl` plus the plain `StartSession` instead.
- `xcrun simctl terminate` / `launch` / `openurl` work (`openurl` is how to drive `sword://`), but can fight the MCP session: after a `terminate` the next `Synthesize` may report `Crashed` when nothing crashed — check for an `.ips` report before believing it, then `InstallAndRun` to re-attach. Driving `simctl` while a session is attached can take Xcode down. A reinstall assigns a new container UUID; re-resolve with `xcrun simctl get_app_container <device> <bundle-id> data`.
- Harmless console noise: `UIAccessibilityLoaderWebShared` duplicate-class warning, `cannot add handler to 0 from 0`.

## The baked content store

`Resources/PSContent.sqlite` + `Resources/Versification-KJV.json` are the app's content and versification. **The converter that produced them is gone; they cannot be regenerated in this repo.** Both are bundled by path.

- Store is **schemaVersion 2 / tokenGrammar v2**; `PSContentStore` refuses anything else. A mismatch would address the wrong chunk slot and return *plausible but wrong* text.
- The FTS source text (`plain_texts`) is shipped, not derived on device — a second derivation would be an untested reimplementation whose bugs silently drop search results.
- **Exactly five modules, no UI to add/remove/pick:** KJV (Bible), MHCC (commentary), and three fixed-role lexicons — `StrongsRealGreek` (`GreekDef`), `StrongsRealHebrew` (`HebrewDef`), `Robinson` (`GreekParse`). The `BundledModules` enum in `AppConstants.swift` is the source of truth. Nothing is unpacked; `Documents/` is empty on a fresh install.

## Architecture

### Launch

1. `@main SimpleScriptureApp` declares a `WindowGroup` around `RootView` and holds the app delegate via `@UIApplicationDelegateAdaptor`.
2. `SimpleScriptureAppDelegate` does only what UIKit owns: `BGTaskScheduler` registration (**must** complete before `didFinishLaunching` returns), `HistoryStore.startCloudSync()`, `AppSession.start()`, and a scene delegate supplying `supportedInterfaceOrientations(for:)` for the rotation-lock pref.
3. `RootView`'s `.task` runs `LaunchCoordinator.prepare()` off the main actor and moves `LaunchPhase` `.preparing → .ready` (or `.failed`). On `.ready` it calls `ReadingWorkspaceModel.start()` and replays any held `sword://` URL.

**Order in step 3 is load-bearing.** Nothing may touch `PSModuleController`, the store or the reader until `prepare()` returns, because it can rewrite `lastRef` (the `lastRef` check, below). That is why `AppSession` parks an incoming URL in `pendingURL`. The scene's `.active` arm waits the same way: `AppSession.resetOnActivationIfRequested` leaves the Settings-bundle reset (`reset_PocketSword`) to `prepare()` until `.ready`, on the same `isReady` flag (pinned by `testActivationResetWaitsForLaunchPreparation`), and `SearchModel.indexMayHaveChanged` does nothing until `configure` has resolved a module.

`LaunchCoordinator` runs `resetPreferences`, the insomnia pref, `MMM` temp cleanup, four one-shot migrations (`DefaultsModuleChoiceRetired`, `DefaultsGlobalFontOnly`, `DefaultsDictKeyCaseFixed`, `DefaultsSwordRetired`) and the `lastRef` check.

- **The `lastRef` check runs at every launch, not once.** A ref the reader cannot resolve is reset to Genesis 1, with both verse positions at 1 and both scroll offsets at 0. It makes the launch render's own lookup on the same string, so a ref that resolves is never rewritten, whatever its spelling. `DefaultsLastRefValidated` is still written; nothing reads it. Don't put the one-shot guard back: a bad ref persisted after it has run blanks the reader at every launch. Pinned by `testLaunchCoordinatorRepairsAnUnresolvableReferenceAtEveryLaunch`.
- `DefaultsSwordRetired` deletes the old engine's `Documents/{mods.d,modules,locales.d,unused}` and `<Caches>/InstallMgr` on upgrade. `PSBookmarks.plist` sits at `Documents/` root, outside those — **never widen the sweep to `Documents/` itself**.
- `resetPreferences()` re-resolves the reading primaries (`reloadLastBible()` / `reloadLastCommentary()`) after `resetModuleSelections()`; the lexicon is left nil deliberately. `AppSession.observeAppStateReset()` reloads the models on `.appStateDidReset`; it must go through `SettingsModel.reload()` (its `isReloading` flag suppresses `didSet` writes that would re-create the deleted keys) and be registered `queue: .main` (the reset runs off the main actor).
- Known, deliberate asymmetries: the reset removes local `bibleHistory` but not the iCloud copy, and the key list is the legacy one plus the per-module `vplPreference`, so rotation lock, the three `lastSearch*`, scroll positions and verse positions survive a reset. Every row of the reader's display menu is cleared: `testResetClearsEveryDisplayToggleTheReaderOffers` takes its keys from `ReaderDisplayToggle.toggles`, so a new row must be added to `resetPreferences()`'s `modulePreferences` too.

### Workspaces

`Read` / `Library` / `Settings` / `Search` in `WorkspaceTabs` — declared in that order, which is also the display order (`TabRole.search` shows Search in the trailing slot wherever it is declared).

**SwiftUI modifiers in the wrong place fail silently** — no warning, no crash, no unit-test failure. Drive the simulator and check the hierarchy. Known traps:

- `tabViewBottomAccessory` is one accessory for the whole `TabView`, not per tab.
- There is no usable `.bottomBar` on iOS 27; items land on top of the floating tab bar.
- **The search-role `Tab` must be declared LAST.** Declared anywhere else, the declared order and the display order disagree, and after every selection SwiftUI's re-push of the tab list (`-[UITabBarController setTabs:animated:]`) re-applies the selection through an index from the wrong order. Measured (iOS 27.2) with Search declared second: tapping Settings selected Library and then Settings, Library went via Search, Search via Settings — 18 of 27 tab changes. Each detour appears and disappears the wrong workspace (building it on first use: Search was configured by the first tap on Library) and cuts the bar's selection animation short, so the pill vanishes and re-enters. It is independent of what the tabs contain and of whether the selection lives in `@State` or the `@Observable` session. Nothing warns, and no test can see it from outside; log `UITabBar.setSelectedItem:` to check.
- **The tab bar's selection animation is evaluated in-process, on the main thread** (sampled: `-[UITabBar setSelectedItem:]` → `UIViewFloatAnimatableProperty` → the private `AnimationKit`, ticking from main-thread display-link callbacks). Main-thread work in the half-second after a tab change lands on its frames.
- **Leaving Search dismisses the keyboard first** (`AppSession.selectedWorkspace`'s setter). A keyboard still up when the next workspace appears is part of that workspace's safe area: the reader was laid out at the keyboard's height (390×442) and then at its own (390×660), which `ReaderScreen`'s size hook answers, as it does any height-only change, with the reader's *previous* offset — replayed, that left a search result opened with the keyboard up (type, tap) where the reader was, under the result's reference in the title. Pinned by `testLeavingSearchDismissesTheKeyboardBeforeTheSelectionMoves`, and by `testOpeningASearchResultWithTheKeyboardUpLandsOnItsVerse` where a keyboard is drawn (see Tests). `ignoresSafeArea(.keyboard)` on the reader's `ZStack` or its `NavigationStack` does **not** stop the hook firing (measured). The hook's height-only path stays: `restoreAfterSizeChange(widthChanged: false)` asks for `lastScrollOffset` whenever one is recorded and the scroll view has not reported itself at it (`scroll(toOffset:)` — see Native reader), and by then the re-rendered chapter has already republished the old offset into it — so any other height change in that window takes the same path, and so does a rotation in the flowing layout (a width change with a row per verse re-anchors on the verse). Only the keyboard trigger is removed here; whether `scroll(toOffset:)` alone keeps a result opened with the keyboard up on its verse is not measured (the headless simulator draws no keyboard).
- **The reader asks for its bottom scroll edge effect by name** (`.scrollEdgeEffectStyle(.soft, for: .bottom)` in `ChapterTextView`). On the automatic style a `ScrollView` gets none under the floating tab bar (a `List` does), with or without the reader's `ignoresSafeArea` and with one pane or two — so the chapter showed through the bar's glass at full contrast and the selection lens refracted it.
- **Navigation stays visible.** Fullscreen/Focus mode and automatic fullscreen are removed. The tab bar and reader/Search navigation bars use `.never` minimisation; reader taps and scrolling do not hide controls. Chapter scrolling, verse tracking, study links and Search keyboard dismissal remain in place.
- A `safeAreaInset(edge: .top)` bar does not combine with a large navigation title — the large-title region expands behind it. `SearchView` and `DictionaryView` pin `.inline` for this reason.
- **Workspaces are persistent.** `SearchView` calls `SearchModel.configure(...)` once per launch (its `.task`, behind `@State configured`), so anything seeding a workspace from outside must drive its model directly (`SearchModel.startStrongsQuery`), and must not assume anything `configure` computes (e.g. `strongsAvailable`) has been computed — both `startStrongsQuery` and `userOptionsDidChange` gate on `module != nil`. Two things are refreshed from outside all the same:
  - **The reader's book, on every entry into Search.** `AppSession.selectedWorkspace`'s setter hands `currentSearchBookName` to `SearchModel.readerBookDidChange`, so the Book scope means the book being read now, not the one open when Search first appeared. It runs no search: a re-run would land on the tab bar's selection animation and replace results a tab change is meant to preserve. Pinned by `testEnteringSearchHandsOverTheReadersCurrentBook` and `testBookScopeUsesTheBookHandedOverOnEntry`.
  - **The search index state, on every activation** (`SearchModel.indexMayHaveChanged`, from the scene's `.active` arm). A background recovery build finishes in the suspended app and tells no one, and "Build Index" over a finished index drops and rebuilds it. It does nothing before `configure` (`module == nil`), unless the coordinator is settled on `.unavailable` or `.ready` (a running build owns the state; a cancelled or failed message stays until the user acts), or while any build holds `SearchIndexBuildGate`; keep all three guards. Pinned by `testSearchAdoptsAnIndexBuiltOutsideTheWorkspace`.

### Reading coordinator (`ReadingWorkspace.swift`)

- `ReadingWorkspaceModel` owns the two `ReaderPaneModel`s (Bible and commentary), the `displayChapter` fan-out, and study-popup routing. Cross-object coordination is method calls; the few remaining `NotificationCenter` observers exist only because something outside the reader posts them.
- **Both panes stay in the hierarchy** (inactive at `opacity(0)`). `displayChapter` renders the polled pane and defers `refToShow` / `pendingRestore` into the other; that deferral is what avoids rendering MHCC on every Bible chapter change. **A deferral only ever waits on a hidden pane**: `mode`'s `didSet` drains a pane as it appears; `displayChapter` drains the pane on screen at once when that is not the pane it polled (a reset polls the Bible whichever pane shows, and so does a bookmark change unless the Bible itself owes a render — `redisplayAfterBookmarksChange()` then polls the pane on screen and the Bible keeps what it owes); and a pane that renders drops whatever it had deferred. A font change (`redisplayWithDefaults()`) polls the **active** pane so that it is the only one rendered. Pinned by `testARedisplayOfTheHiddenPaneLeavesNoDeferralOnThePaneOnScreen`, `testRenderingAPaneDropsWhateverItHadDeferred` and `testAResetWhileTheCommentaryShowsRerendersTheCommentary`.
- `ReaderPaneModel.render` writes `lastRef` (toolbar title and relaunch restore both read it).
- Links arrive as `pslink://` URLs through the reader's `OpenURLAction` and open a `StudyPopupSheet`. The override is `routesChapterLinks(to:)`, and it must be on **every** `Text` that can carry a link: a heading row is a sibling of the verse text, not inside it, and a Psalm title has Strong's and morph markers of its own — without it a tap on one does nothing (measured 2026-11-11, iOS 27.2: with the modifier off `HeadingRow`, the `<04210>` marker in Psalms 3's title was found, hittable and tapped, and no popup opened). `testAPsalmTitlesMarkersAreLinksTheReaderRoutes` pins that the title's text carries its links; the XCUITest `testStrongsLinkInAPsalmTitleOpensItsLexiconEntry` taps one and pins that it reaches the pane.
- **A search result's highlight lasts for the chapter it was opened in.** `clearSearchHighlight()` ends it in **both** panes (the hidden one follows to the new chapter through its deferral) on every way out: `page(forward:)`, `selectReference`'s other-chapter path, `showRoutedMode` (a bookmark, a history row, a `sword://` link, the next search result) and `.appStateDidReset`. Redrawing the same chapter (font, display toggle, bookmark edit, Bible ⇄ commentary) keeps it. **Open a result with `openSearchResult(_:module:terms:mode:)`**, which assigns the terms *after* the open: the open is a route, so terms set before it are wiped and the result opens unhighlighted, with nothing failing. Pinned by `testLeavingASearchResultsChapterEndsItsHighlightInBothPanes`, `testASearchResultsTermsGoOnAfterTheOpenThatEndsThePreviousHighlight` and `testAResetEndsTheSearchHighlight`.
- **Chapter paging restores no position, in both directions.** `previousChapter()` / `nextChapter()` go through `page(forward:)` with `.none`. The verse-position defaults hold the verse in the chapter being *left*, so restoring them on paging lands on a wrong verse. Don't reintroduce a restore. Two entry points: the chevron toolbar buttons, and a horizontal swipe on the reader (left = next, right = previous).
- **The chapter swipe** is a `DragGesture` on `ReaderScreen`'s pane `ZStack` (one recogniser for whichever pane shows), attached with **`.gesture`, not `.simultaneousGesture`**: the chapter text is selectable, and dragging a selection handle is a sideways drag — recognised simultaneously, extending a selection turned the page (measured, iOS 27.2). At ordinary priority the text's own gestures win, a swipe on plain text or a link still pages, and vertical scrolling is unaffected. `ChapterSwipe` (`SwiftUIReaderChrome.swift`) is the pure swipe-versus-scroll classifier — distance, projected distance, 2:1 horizontal dominance — pinned by `testChapterSwipeClassifiesAFinishedDrag`. `ReadingWorkspaceModel.page(_:)` gates it on the flags that disable the chevrons, because `page(forward:)` clears the search highlight before its boundary check.
- **Paging starts the new chapter on a new scroll view.** `displayChapter`'s `.none` (paging is its only caller) hands both panes `PaneRestore.chapterStart`, which bumps `ReaderPaneModel.scrollSurface` — the `ScrollView`'s `.id` in `ChapterTextView` — and resets `scrollPosition`. Scrolling the *old* scroll view to the top (what `.none` still does for its other producers) does not land reliably after a chapter swap: the chapters share row ids, and the old view keeps its anchored row and its momentum. Measured: 7 chevron pages in 120 and 8 swipes in 32 left verse 1 in the wrong place (too low, drifting, or shifted sideways); 0 in 152 with a new scroll view. Don't "simplify" it back to a `scrollTo(edge: .top)`.
  - `.chapterStart` also **persists verse 1 / offset 0 itself**. A scroll view that starts at the top reports no movement, so nothing else would write those keys, and they would hold the position in the chapter being left (`setToPreviousChapter` writes the destination's *last* verse). Pinned by `testPagingStartsANewScrollSurfaceAtThePersistedTopOfTheChapter`. `showRoutedMode` deliberately stays on `.none`: persisting verse 1 there would clobber the verse an inbound `sword://` URL just wrote.
  - **The pane a page turn is deferred into has the same two keys written when the turn is deferred** (`ReaderPaneModel.deferRender(of:restore:)`), not only when it drains. Every other restore `displayChapter` builds comes from a pane's position keys, and until the pane has shown the new chapter they describe the old one — to a relaunch (`.scroll`) and to any redisplay. An owed `.chapterStart` then outlasts a redisplay (`.verse(1)`, an offset, no saved position); a verse past the first replaces it (a `sword://` route writes the Bible's verse key for a commentary destination too, and draining `.chapterStart` would persist verse 1 over it); an offset or `.none` never replaces an owed verse. `selectReference` re-aims a chapter a pane still owes through the same method rather than scrolling a document about to be replaced. Pinned by `testADeferredPageTurnSurvivesARedisplay`, `testPagingFromTheCommentaryLeavesTheBibleAtTheChapterStart`, `testABookmarkChangeKeepsTheVerseADeferredPaneWasSentTo` and `testPickingAVerseInTheOpenChapterReachesThePaneThatHasNotRenderedIt`.
  - The landing was intermittent, so `testSwipingTheReaderPagesChapters` (which pages from the foot of a chapter and compares against the chevron's landing) is a necessary check, not a sufficient one.
- **A page turn slides.** The swap between scroll surfaces is animated by `ChapterPageTransition` (`SwiftUIReaderChrome.swift`): the new chapter comes in from the right going forward and the left going back, pushing the old one out the other side, for a chevron and a swipe alike. Under Reduce Motion the two cross-fade in place. It travels the page's width plus the side safe-area insets (`overhang`), so in landscape on an iPhone the page leaves the screen rather than stopping in the margin beside the sensor housing. Each of these is measured (iOS 27.2), not stylistic:
  - **The slide is keyed on `ReaderPaneModel.pageTurn`, not on `scrollSurface`.** `page(forward:)` bumps `pageTurn` on the active pane only. The other pane bumps its surface later, when a Bible ⇄ commentary switch drains its deferred `.chapterStart`, and that swap must happen in place — it is a pane appearing, not a page turning. Pinned by `testOnlyThePaneOnScreenTurnsAPage`.
  - **The transition reads the direction from the pane when it runs; it does not store it.** SwiftUI removes a view with the transition value it was *last given*, which for the scroll view being left is the previous turn's. With the direction stored (`.push(from:)`), paging forward and then back sent the old chapter out to the left while the new one came in from the left too.
  - **The scroll view being left stays live for the length of the slide**, still coasting on any flick, and keeps reporting: paging straight after a flick, it sent 26 offsets and topmost verses from the old chapter in the 420 ms after the new chapter's position was persisted. `scrollOffsetChanged` / `topmostVerseChanged` therefore take the reporting surface (`from:`) and drop a replaced one; `ChapterTextView` captures `pane.scrollSurface` once per body and threads it into every callback. Pinned by `testAScrollViewBeingLeftCannotOverwriteTheNewChaptersPosition`. Don't drop the parameter, and don't read `pane.scrollSurface` inside a callback — that is always the current one.
  - **The page does not follow the finger during a swipe, and at `.gesture` priority it cannot.** SwiftUI holds the drag back until the text's own gestures have had the touch and then delivers all of it at once: every update of a 1.6-second drag arrived in the same millisecond as its end. Tracking the finger would need `.simultaneousGesture`, which is the attachment that made a selection drag turn the page.
- **A swipe that turns the page fires one light impact** (`sensoryFeedback` on `ReaderScreen`, triggered off `page(_:)`'s return value). A swipe that goes nowhere — a scroll, or back from Genesis 1 — is silent, and so are the chevrons. Pinned by `testASwipeReportsWhetherItTurnedThePage`. The simulator has no haptics: the trigger can be checked there, the feel only on a device.

### Content reader (render path)

**The app reads only from the baked store; there is no fallback.** Failures are split into **fatal** (store missing, schema/grammar mismatch, missing chunk sizes, bad versification — a crash beats a blank app) and **loud-and-nil** (one bad chapter must not brick the app). `PSContentReader.swift`'s header lists which is which; keep it accurate.

- `PSContentStore` — read-only SQLite + chunk framing, serial queue, zlib `uncompress()` (not `Compression.framework`; blobs are zlib-with-header with exact `raw_size`). Reads chunk sizes from `content_meta`.
- `PSChapterExpander` — tokens → the exact HTML the SWORD markup filters emitted. A disabled toggle **skips** its token. `Options.forHeading`: a title token is headings-gated in a chapter record but unconditional inside a stored heading.
- `PSChapterAssembler` — the chapter accumulator loop, quirks included. Its `entryCount` is **not** a verse count (it advances for skipped entries) and is pinned by `chapter-loop-counters.tsv`. Verse highlighting inserts at UTF-16 offsets over `NSMutableString`; redoing it over `String.Index` is a different algorithm.
- `PSBookOSISResolver` — book name → OSIS abbreviation, and the whole versification layer (`book(at:)`, `verseMax`, `nextChapter` / `previousChapter`, `displayRef`). next/prev return **nil** at Genesis 1 / Revelation 22 (not clamped — a clamped ref would turn a no-op into a full re-render). `displayRef` returns the un-munged `longName` form that call sites munge downstream.
- `PSRefParser` — free-text refs, `<book> [<chapter>[:<verse>[-<verse>]]]`, single book, deliberately narrow (header documents each omission). Its production callers are `URLRouter` (inbound `sword://`) and `ReadingStateStore.snapshot()`, which parses the persisted `lastRef` into the session's mirror. It is **wider** than `PSBookOSISResolver.resolve(ref:)`, so anything persisting a parsed ref must check the resolver accepts the string it actually stores — after `createRefString`, which is case-sensitive where the book lookup is not and can break a ref that resolved without it ("MALACHI 3" → "MALACH1 3"). `URLRouter.route(for:)` does this: a link's own spelling is kept only when its munged form resolves, otherwise the parser's canonical ref is stored. Pinned by `testEverySpellingInEveryCasingPersistsARefTheReaderResolves`.
- `PSRefLinkRouter` — pure `showRef` routing predicate; an unrecognised module type defaults to bible.
- `PSContentReader` — module selection, per-module option prefs, bookmark-highlight lookup. `chapterDocument(module:ref:kind:)` is **the render path**. `chapterBody(...)` returns engine-exact HTML and is kept as a **test oracle** — `PSChapterDocumentParityTests` proves the native document matches it. The bookmark highlight is looked up for a **Bible only**, in both emitters (the assembler's lookup sits in its `.bible` branch; `PSChapterDocumentBuilder` gates on `config.kind`): a commentary row's number is the first slot of a verse *range*, so a Bible bookmark would paint a whole section. Pinned by `testBookmarkHighlightIsLookedUpForABibleOnlyInBothEmitters`; the parity comparison passes no colours and cannot see it.

### Native reader (`PSChapterDocument.swift`, `SwiftUINativeReader.swift`, `PSEntryDocument.swift`)

- **Two emitters over the same tokens, deliberately.** `PSChapterExpander` → HTML; `PSChapterDocumentBuilder` → `ChapterDocument`. Their independence is what makes the parity test meaningful — **do not make one call the other.** The chapter corpus is a closed set of six inline tags, which is why there is no HTML parser dependency.
- **Lexicon entries and footnotes have their own renderer** (`PSEntryDocument.swift`) with a wider vocabulary (`br`, `a name=` / `a href=`, `sup`/`sub`, `q`, `bib`).
  - Hebrew and Greek Strong's entries shape their key-anchor preamble differently. The "swallow the `<br />` after the key anchor" rule means *immediately* after; `testGreekLexiconKeepsItsLemmaLineBreak` pins it.
  - A link's run range is bounded at the anchor's **open** (`runs.count`), and re-applied at a `<br />` block boundary. `testEveryLexiconCrossLinkIsBoundToItsOwnAnchorText` and the synthetic `testCrossLinkSpanningALineBreakKeepsBothHalves` pin it.
  - An `OpenURLAction` that returns `.handled` with no handler swallows the tap. Claim `.handled` only when there is a handler; otherwise `.systemAction`.
  - Cross-links resolve in place in `StudyPopupSheet` (a `trail` + Back), not by stacking sheets. The `G`/`H` prefix comes from the **target** module (317 links go Greek → Hebrew).
- **The reader's side gutter is a scroll-content margin** (`contentMargins(.all, …, for: .scrollContent)`), not padding inside the content. The scroll view re-anchors to a row as lazy heights settle and aligns the row's leading edge with the content's; as padding, that left the chapter resting shifted left by the gutter, flush against the screen edge (1 chevron page in 120). Don't move it back.
- **Scroll position is identity**, via `ScrollPosition(id:)`. In prose mode rows are paragraphs, so `scrollToVerse` lands at the top of the verse's paragraph (`rowID(containing:)`), and a verse number being in the hierarchy says nothing about where the reader rests (measured 2026-11-11, iOS 27.2: flowing Genesis 3:10 rests at verse 1, verse 10's number 900 pt down an 874 pt screen). **Verse 1 lands on the chapter's first row when that row is a bare title** (Headings on: row 0), in both layouts; sent to its own row with a row per verse, it rests with the title behind the navigation bar (measured: y 89.9–110.6 at 18 pt, the reading area starting at 116). A first row with text of its own — a commentary's chapter summary — is not verse 1's, so "View in Commentary" on verse 1 opens on verse 1's record. Pinned by `testALandingOnVerseOneLandsOnTheTitleRowAboveIt` and, for the reference picker with a row per verse, the XCUITest `testPickingVerseOneShowsTheChapterTitleWithHeadingsOn` — its flowing half passes with verse 1 sent to its own row too (Genesis 1's title heads verse 1's paragraph; a psalm whose `PSALM n.` is a paragraph by itself is in the unit test only); a launch at the top of a chapter is measured too, with a row per verse and with a flowing psalm. The Headings toggle, a link or search result at verse 1 and a rotation at the top of a chapter are model only.
  - Applying a scroll in the same update as a document change does nothing; `apply(_:)` defers by one update. `restoreAfterSizeChange` inlines its own copy of `apply`'s `.verse` body so the rotation suppression clears in the same hop — don't de-duplicate them.
  - **`ScrollPosition.scrollTo(y:)` is inset-relative**, and the persisted offset (`contentOffset.y + contentInsets.top`) matches it on purpose. This is measured, not a bug. At rest the sum is 0.
  - **An offset handed to `ScrollPosition` stays in it after the scroll view has gone there, and SwiftUI applies it again whenever the content or container size changes — as a raw content offset** (measured 2026-11-11, iOS 27.2: 1099 rests at content offset (-16, 983) and comes back as (0, 1099), the chapter one top inset further on and flush against the left screen edge). The lazy rows are re-measured as the app goes to the background and at the first accessibility read of the reader — any XCUITest hierarchy query — and the pane saves the moved place: left in, a launch restore walks on at every launch that is left (1099, 1215, 1331, 1447; 3 launches in 3), and a bookmark redraw, the commentary's restore and a flowing-layout rotation move the same way. So `ReaderPaneModel` holds an offset only while the scroll is on its way. `scrollOffsetChanged` takes it out (`isPositionedByUser = true`, the state a finger leaves) when a laid-out report has the scroll view at it, or pinned at the chapter's end short of it — a report a size change is keeping from being saved as a scroll counts too. `scroll(toOffset:)`, the one caller of `scrollTo(y:)`, asks nothing of a scroll view whose last report on this chapter and scroll surface (`reportedSample`) has it there — the size hook's replay after a landing, a bookmark redraw in place: such a request moves nothing, so nothing reports and the offset would never come out. Don't call `scrollTo(y:)` directly, and read `ScrollPosition.y`, not `.point` (nil for a y-only offset). 0 of 11 launches that were left moved (measured). Pinned by `testAnOffsetIsTakenOutOfTheScrollPositionOnceTheScrollViewIsThere`, `testABookmarkRedisplayAsksNothingOfAScrollViewAlreadyThere` and the XCUITest `testARestoredPositionKeepsItsGutterWhenTheAppIsLeft`, which asks nothing of the app between a launch and leaving it. Open: while the offset is held, a size change that arrives with the landing applies it raw (seen in a flowing-layout rotation, where the size hook then sends the scroll view back; in no launch).
  - **A width change re-anchors on the verse; a height-only change keeps the offset.** `ReaderScreen`'s size hook passes `widthChanged` to `restoreAfterSizeChange`. Height alone (the bars settling at launch, a keyboard going) re-wraps nothing, so a recorded `lastScrollOffset` is kept exactly — replayed to a scroll view the change moved, nothing asked of one that reports it is there; with none recorded (0) the hook re-issues the row of `currentShownVerse` by id. A width change re-wraps every row, so the old width's offset names different text, and a pane with a row per verse scrolls to `currentShownVerse` and zeroes `lastScrollOffset` — the height-only step that follows a rotation would otherwise replay it. It does so only when the verse is measured (`shownVerseIsMeasured`: the view reported it or a restore named it; false after an offset restore that moves the scroll view until a row reports, or a launch restore would be dragged to verse 1), no offset restore is in flight and the pane owes no render. An offset the scroll view is already at under a measured verse — a bookmark change's redisplay — keeps the verse and arms no landing: nothing moves, so no row reports. Pinned in the model by `testAWidthChangeReanchorsOnTheTopmostVerseInsteadOfReplayingPixels` and `testABookmarkChangeKeepsTheMeasuredVerseForTheNextRotation` (a bookmark and then a rotation is not driven on the simulator), and where a rotation lands by the XCUITest `testRotatingTheReaderKeepsTheVerseBeingRead`. Measured 2026-11-11 (iOS 27.2, iPhone 18 Pro, 18 pt, Genesis 1):
    - With a row per verse, from verse 15 scrolled 68 pt out, its row's top rests 0.1 pt above the navigation bar's bottom edge in landscape and again in portrait, the same over three round trips. With the offset replayed instead, landscape rests on verse 26.
    - The flowing layout keeps the offset on a width change too — a paragraph is one scroll target, and re-anchoring would jump to its first verse — so landscape shows other text. From an offset landscape can reach, there and back returns to the starting frames exactly. From one it cannot (verse 17 at the top, offset 1278), landscape pins at the foot of the chapter on verse 27, and portrait came back on verse 15 when the size hook still handed the offset to a scroll view that was already there; not re-measured since.
    - The offset saved after a width change is about one row early for a cold launch. By the row arithmetic the scroll view counts the 7 rows above those it has laid out at the new width as 260 pt where they measure 316, so landscape saves (15, 631) where a launch needs 687, and a relaunch there opens on verse 14. The verse key is right, and the pair is exact again back in portrait.
  - Launch offset restore: the reader's size settles in steps during launch, so the size hook fires (height-only steps); `restoreAfterSizeChange` prefers an outstanding offset restore. The first geometry publish is an unlaid-out scroll view and must not be persisted. `ReaderScrollSample` + `outstandingOffsetRestore` give `scrollOffsetChanged` a three-way gate (drop unlaid-out samples; clear on landing within 2 pt; give up at `maxOffset` when unreachable), released by `userBeganScrolling()`. Pinned by `testUnlaidOutGeometryDoesNotOverwriteThePersistedScrollOffset` and `testUnreachableOffsetRestoreGivesUpAtTheScrollViewsMaximum`. Open, not fixed: when the scene goes active before the reader's first layout, the restore's deferred scroll runs before the scroll view exists, the lazy stack starts at the saved offset with nothing above it measured, and the reader opens about two verses further on, gutter intact; the next re-measure saves that place (measured 2026-11-11, iOS 27.2: 2 of 14 XCUITest relaunches, verse 11 at the top where verse 9 was saved; 0 of about 33 `simctl` launches). An XCUITest must not assert which verse a relaunch restores.
  - An offset restore carries the verse its keys pair with it (`offsetRestoreVerse`), so a scroll persisted before the view has reported a verse writes the saved one back. Without it the first such scroll — the rows settling a few points is enough — writes a new pane's verse 1 over the saved verse and retitles to `…:1` with the reader correctly mid-chapter. It is kept apart from `currentShownVerse` on purpose: seeded there, the pre-landing report of verse 1 would be taken for a move and persisted. It ends at any persist, any newer restore, and the view's first report that counts as a measurement — one that only confirms the pane's verse too: that report persists nothing, and a saved verse still armed after it is what the next scroll writes over the verse just reported. Pinned by `testAnOffsetRestoreKeepsTheSavedVerseUntilTheViewReportsOne` (model only). On the simulator the title after a launch restore names the saved verse: 12 of 12 `simctl` cold launches from a seeded mid-chapter position read `Gen 1:14`, none `…:1` (measured 2026-11-11, iOS 27.2, all in the ordinary launch order). To judge where the reader is, XCUITests assert on reader content all the same, not the nav-bar title: the title follows the pane's verse, not where the scroll view rests, and it reads right over a reader in the wrong place (`Gen 5:29` over verses 2–4 in the keyboard case under Workspaces).
  - The prose row set is cached on `ReaderPaneModel.paragraphs` (invalidated by `document`'s `didSet`). Never call `ChapterDocument.paragraphs` from a view body. The cache is on the model, not the value type, to keep `ChapterDocument`'s synthesized `Equatable` and memberwise init that the parity tests use.
- **Verse layout honours verse-per-line.** VPL off: prose, breaking at the KJV's pilcrows (all at verse starts). VPL on (default — an absent `vplPreference_<module>` reads as on via `UserDefaults.psBool`): one row per verse. A commentary always breaks per verse (MHCC has no pilcrows). The prose join is `ChapterTextRenderer.flowedPieces`: a space after each verse but the last (the engine's newline between entries), none after a verse that already ends in one, added outside the verse's bookmark colour and search jacket. The gap after a verse number is U+202F (no-break), not a hair space: with a breakable gap the only break near a verse boundary is after the number, and 133 of 1,655 numbers were left at a line end (measured, CoreText); none with U+202F plus that space. Pinned by `testFlowedVersesAreSpacedAndNumbersStayWithTheirVerse`.
- **A Bible chapter has a row 0 only when its intro has something to show.** A title token that leads a record is hoisted into `ChapterVerse.headings` (`hoistLeadingTitles`; all 1,184 KJV chapter titles are slot 0, shaped `" " + <title>`). With Headings on, row 0 is therefore a heading-only row — where a landing on verse 1 goes (Scroll position, above) — and `VerseRow` / `ParagraphRow` skip its text when `hasVisibleText` is false (an empty `Text` still takes a line). With Headings off no KJV chapter has a row 0: in the 1,184 chapters that carry a title the intro is that title's leading space and is withheld, and the other five have no intro row to begin with — though `entryCount` still counts the slot. Keep both layouts in each: a builder regression fails only the flowing-prose halves, and the row-per-verse halves fail only with the row view's guard gone (measured 2026-11-11, iOS 27.2; their comments say which removal fails where).

### Dictionary

- `dict_keys.key` is `COLLATE NOCASE` as defence in depth; both producers return the module's true key casing, and `PSContentStoreTests` asserts both casings resolve for all 15,824 keys. `DefaultsDictKeyCaseFixed` sweeps `<Caches>/cache-*` key caches by prefix.

### Search (`PSSearchEngine.swift`, `PSSearchQuery.swift`)

Search results expose a long-press **Copy Verse** action (reference plus normalized
verse text). The results list is `.scrollDismissesKeyboard(.immediately)`: a scroll
is meant to put away a keyboard that is on screen. That has not been observed on
iOS 27.2 (its test has only ever skipped); with none drawn the scroll leaves the
field focused (measured — see Tests). Leaving the Search workspace takes the focus
out of the field either way (see Workspaces — the order there is load-bearing);
reselecting the Search tab focuses the existing search field. Preserve the query,
results, module and persisted options during these
interactions. "Find all occurrences" (`SearchModel.startStrongsQuery`) is the
deliberate exception: it moves Search to the module that carries Strong's numbers
when the current one does not, and sets the scope to All as a model-originated
write — shown in the picker, not persisted until the user next changes an option.
Left on the module Search was last on (sticky for the launch, not saved) or on the
saved scope, a number with thousands of occurrences reads "No Results" — or, under
a saved Book scope, silently lists one book's share. Pinned by `testStrongsQueryMovesSearchToTheModuleThatCarriesStrongs`
and `testStrongsQuerySearchesTheWholeBibleWhateverScopeWasSaved`.

Each of these fails **silently** if "simplified":

1. `SQLITE_TRANSIENT` on every `sqlite3_bind_text`; SQL passed to `prepare_v2` / `exec` via `withCString`. Otherwise every query matches nothing.
2. `SQLITE_OPEN_FULLMUTEX` + `sqlite3_busy_timeout(2000)` and **no** serial queue, so a ~30 s build doesn't block every keystroke's query.
3. The FTS5 schema, its seven columns and their order, and `ORDER BY rowid` are fixed.
4. `PSSearchQuery.cleanDisplayText` runs **before** the emptiness test in the build loop, so it decides which rows exist.
5. The index is `<Caches>/search/<module>.db` (`AppPaths.searchIndexPath(for:)`), shared directory — **`dropIndex` must not remove the directory.** A cached engine whose file is gone reopens on demand.
6. The default `queryOperation` asks the engine for `SearchModel.resultLimit + 1` rows (the list cap is 1,000). That extra row is the only way `setResults` knows the list was cut (`resultsWereTruncated`, the header's `SearchResultCountTruncatedFormat`); asked for exactly the cap, the list is never marked as cut, the header gives the cap as the count, and no unit test fails — only the XCUITest `testSearchHeaderSaysWhenTheListWasCut` (measured 2026-11-11, iOS 27.2: the header for "the" read "1,000 Results").

`cleanDisplayText` (strips inline `<H0430>` markers) and `foldForIndex` (diacritic fold for `text_norm`) are pinned to known vectors in `PSSearchIndexParityTests`; changing either stops queries matching indexes already built on devices. Bump `PSSearchEngine.schemaVersion` to force a rebuild. `engine(forModuleName:)` returns a shared instance. Cancellation belongs to `SearchIndexCoordinator`.

Query-side rewrites stay query-side. `PSSearchQuery` straightens typographic double quotes (`straighteningQuotes`) and ORs the `ae` / `æ` spellings of a term (`ligatureSpellings` — the KJV prints Cæsar and Judæa, and `text_norm` keeps the ligature) on a copy, at query time: not in `foldForIndex`, and never written back to `SearchModel.query`, which the field and the saved search history hold as typed.

**One reading of the input makes both the query and its highlight.** `PSSearchQuery.textTerms` is every text arm of the builder as a list of terms — Exact (trim, strip one pair of quotes), quoted phrases, the words Fuzzy runs as a prefix, the spellings. `fts5Expression` renders that list and `highlightTerms(fromUserInput:…)` hands the same list to the highlighters as `SearchHighlightTerm`s; `SearchModel.highlightTerms` only forwards. A token with no letter or digit in it (a stray `&` or `-`) is no term in All and Any: as a phrase with nothing in it, it matched no verse and emptied an All search (`faith & works`: nothing, where `faith works` finds 15 verses; pinned by `testAnAllSearchLeavesOutAWordWithNoLetterOrDigit`). Don't work the terms out a second time anywhere. `SearchModel` used to, with a copy of the rules kept in step by hand, and each rule the copy lacked (the Exact trim, the stripped quotes, typographic quotes, the spellings) was a search that found its verses and marked nothing.

**A term is marked where the query matched it: on whole index tokens.** Both highlighters — the result row (`SearchHighlightedText`) and the reader (`ChapterTextRenderer.applyHighlights`) — ask `PSSearchQuery.highlightRanges(of:in:)`. It cuts the text as `unicode61` cuts `foldForIndex(text)` (runs of letters and digits, the marks the fold deletes stepped over) and marks a term where its tokens stand in a row. So `the` is not marked inside "there"; a phrase is marked across the punctuation between its words; `LORD's` and `Beer-sheba` mark "LORD’S" and "Beer–sheba"; and a term with `matchesPrefix` (a word Fuzzy ran as `word*`) is marked over every word that begins with it. Don't put a substring search back in either highlighter. It looks right for a long word (`God`: 3,836 of 3,892 rows marked exactly as matched) and is wrong on most rows for a short one: measured on the KJV index, the rows a search for `the` found had 93,567 marks where FTS5 matched 63,944 words, and `LORD's` typed with a straight apostrophe was marked in none of the 131 verses it finds.

- The terms are made when the query runs and travel unchanged into the reader (`openSearchResult`), so a row and the chapter it opens mark the same words. The rows are not told the Fuzzy or Strong's options as they stand; they were, and re-marked the search on screen the moment a toggle was flipped, before any query had run with it. `SearchModel.highlightTerms` is still assigned when a query starts, not when its rows land, so for the length of a query (a frame or so) the previous rows are drawn with the new terms — as before, and left alone.
- No term is dropped for being short. One-character terms were, when `a` would have marked every a in the verse; as whole words the drop would only cost marks (an Any search for `I am` finds 6,031 verses, 5,220 of them on their `I` alone).
- The reader matches a verse's words joined, with the marker runs left out. "LORD" is two runs ("L" + "ORD"): a word spans a run boundary in 5,825 KJV verses, and no marker sits inside a word (measured at all 32 combinations of the display options).
- **A Strong's search has no terms.** Its rows mark the verse's `word_map` surface words for the number, as whole words, and the reader marks nothing. `PSSearchEngine.surfaceWords` takes the `<divineName>` markup off a surface at read time: with it on, the surface is in no verse, and H3068 marked a word in 1 of its 5,521 rows. A row marks its own words when it has any and the query's terms otherwise, by what it holds (`SearchResultRow.highlightTerms(orQuery:)`). `word_map` has no positions, so a surface word is marked wherever it stands in the verse — about 3% of (verse, number) pairs mark a word the number did not tag (John 3:16 has "that" under two numbers) — and a word of a Psalm's title is not in the row's text at all (H4210 "A Psalm": 57 rows, none marked).
- Pinned by `testASearchTermIsMarkedWhereTheQueryMatchedIt` (held to FTS5 on one-row tables: a verse is marked exactly when the query's own expression matches it), `testTheHighlighterCutsWordsWhereTheIndexDoes` (the tokenizer against the simulator's SQLite, character by character), `testAFuzzyTermIsAPrefixExactlyWhereTheQueryRanOne`, `testAResultRowMarksASearchTermAsAWholeWord`, `testAStrongsRowMarksTheWordsTaggedWithItsNumber`, `testTheReaderMarksASearchTermAsAWholeWord` and `testTheReadersWordsAreTheWordsTheSearchMatched`. The marks are attributes, not accessibility values, so no XCUITest can see them.
- Not modelled, and in neither module's text (`highlightTokens`' comment has the list): FTS5's tables are Unicode 6.1's, so it takes a code point that was unassigned then (the Turkish lira sign, an emoji assigned since) for part of a word; its own case folding goes further than `foldForIndex` for eleven letters (ſ, a final sigma); and a letter that decomposes to, or is followed by, a mark the fold keeps is cut differently (Devanagari nukta letters, kana voiced marks). Baked, and not fixable here: MHCC's plain text has 145 words its chapter body lacks (six passages, each stretch after an `&c`), so a search can find a passage on a word the reader does not have.

### Module controller

`PSModuleController` (singleton, `defaultModuleController`) holds the primary Bible / commentary / dictionary as **`String?` names** (`primaryBibleName` etc.) plus ref-string helpers. `nil` means not yet resolved.

### Display preferences

The split by scope is load-bearing:

- **Per-module content toggles** (Strong's, morph, headings, footnotes, cross-refs, red-letter, verse-per-line) live in the reader's `ToolbarOverflowMenu`, built by `ReaderDisplayToggle.toggles(forModule:store:)`. Keys are `"<pref>_<ModuleName>"`, gated on the baked feature set (`content_meta` `module.<name>.features`, via `PSContentStore.moduleHasFeature`).
  - **KJV shows exactly six rows**: Strong's, Morph, Headings, Footnotes, Red Letter, Verse Per Line. **No cross-references** — KJV has no scripref feature. Don't "fix" this.
  - **MHCC has no rows**, so the commentary declares no overflow menu and has no ••• button (measured, iOS 27.2: no `…OverflowBarButtonItem` in Commentary mode, the rest of the bar unmoved). `ReaderScreen` declares the `ToolbarOverflowMenu` inside its `.toolbar` builder under `if !chrome.displayToggles.isEmpty` — not the `toolbarOverflowMenu` modifier with its content gated (the system still draws the button, and it opens an empty menu), and not a conditional modifier on the panes (that changes their identity on every Bible ⇄ commentary switch and drops their scroll state and deferred work). The row sets are asserted by `AppStateStoresTests.testDisplayTogglesMatchBakedFeatureSets`; the button, and the Bible's menu being exactly its six rows, by the XCUITest `testDisplayTogglesAppearForBibleAndNotCommentary`.
- **Global**: font name + size and device options, in `SettingsView` (`SwiftUISupportingViews.swift`). **One font for the whole app**: `ChapterTextRenderer.Style.current()` reads only unsuffixed `fontNamePreference` / `fontSizePreference`.
- `EntryTextView` honours the same keys, with a legibility floor `EntryTextView.minimumBodySize` (14). Its default `style` is a `UserDefaults` read made when the parent's body builds it, which subscribes that body to nothing: a parent that stays on screen across a Settings change (the Library's `DictionaryEntryView`) passes `ChapterTextRenderer.Style.current(observing: settings)` instead. The two unused-looking reads in that helper are the subscription; pinned by `testEntryStyleReadSubscribesToTheFontSettings` and, on screen, by the XCUITest `testOpenDictionaryEntryFollowsAFontSizeChange` (measured 2026-11-11, iOS 27.2: with the default style an entry left open keeps its size across a Settings change — a line 16 pt tall at size 10 and still 16 pt at 36, since coming back to the Library tab rebuilds nothing; with the read, 16 pt to 41). The Strong's arm uses the system face (`usesSystemFace`). `AppConstants.defaultFontSize` (20; default face Georgia) is the single absent-key fallback (Swift-only; `globals.h` has no counterpart).
- Code2000 is no longer bundled or offered. Existing saved font preferences are not migrated, and not rewritten: a saved name the system cannot supply is drawn as the default, and Settings names the default (`StudyFonts.resolved`, used by `ChapterTextRenderer.Style.current()` and `SettingsStore.snapshot()`). The font picker lists `StudyFonts.all` — the catalogue filtered through `StudyFonts.isInstalled` when first read: 36 of 43 names on iOS 27.2. Four names with no font file of their own (Heiti SC / TC, Bangla / Telugu Sangam MN) stay offered because the system answers for them with their successors. Pinned by `testFontPickerOffersOnlyFontsTheSystemCanSupply`, `testASavedFontTheSystemLacksRendersAsTheDefault` and `testSettingsSnapshotShowsTheFontInEffect`.

### Constants: `globals.h` ↔ `AppConstants.swift`

**Dual-maintained.** `globals.h` is the source of truth for `Defaults*` keys, notification names, `ShownTab`, `PSSearch*`, `ModuleType`, `ATTRTYPE_*`, `SW_OUTPUT_*_KEY`, `SWMOD_*`. `AppConstants.swift` mirrors every wire string **byte-for-byte**. The persisted key often differs from the macro name (`DefaultsLastRef` → `"lastRef"`). Change one, change the other, or persisted data breaks.

- Retired keys (`DefaultsKJVRemoved`, `DefaultsMHCCRemoved`, `DefaultsStrongsGreekModule`, `DefaultsStrongsHebrewModule`, `DefaultsMorphGreekModule`) stay declared so the names aren't reused; `DefaultsModuleChoiceRetired` clears them.
- `ShownTab` ordinals may be persisted — do not renumber or delete. New code uses `ReadingMode` / `Workspace`.
- There are no Objective-C consumers of a generated Swift interface header. `@objc` annotations on model types are inert; don't read one as evidence of an Obj-C caller. `NSObject` subclassing on persisted model types is relied on by the byte-locked formats.

### Persistence

- `UserDefaults` with keys from `globals.h` / `AppConstants.swift`; per-module prefs are `"<PrefName>_<ModuleName>"` via the `UserDefaults.ps*(…forModule:)` extension.
- Reading history (`bibleHistory`) syncs through `NSUbiquitousKeyValueStore`; `HistoryStore` owns observer, merge/dedup/cap, write-back and `addEntry(mode:)` (the byte-locked `[ref, "0", mod, NSDate]` row). `startCloudSync()` calls `synchronize()` on the store **after** registering the observer, so that changes made while the app was not running can come back through the same notification and merge. Only that order is pinned, against a stub that posts the notification from inside `synchronize()`. That iCloud answers this way, and that the call is inert without the iCloud entitlement (Debug/Release), come from the API's documentation and have not been measured: that takes two devices on one account and a Distribution-signed build. `addEntry` reads `lastRef` from its own injected `defaults`, and seeds the persistent domain before a first entry **only when that store is `UserDefaults.standard`**: `persistentDomain(forName:)` / `setPersistentDomain(_:forName:)` address the domain by name whichever instance they are called on, so made through an injected suite they would empty the host app's real `bibleHistory` on every unit-test run. Pinned by `testStartingCloudSyncAsksForChangesMadeWhileTheAppWasNotRunning` and `testAddEntryThroughAnInjectedStoreLeavesTheAppsOwnHistoryAlone`.
- Bookmarks: `Documents/PSBookmarks.plist` at the **root** of `Documents/` (see `DefaultsSwordRetired`).
- Derived data lives in Caches: search indexes and lexicon key caches.
- `bibleScrollPosition` / `commentaryScrollPosition` are raw `UserDefaults` string keys, written as `"%d"` of a `CGFloat`.

### URL handling

`sword://` is registered in `misc/icon/Info.plist`. URLs arrive via `onOpenURL` → `AppSession.open(_:)`; before launch prep finishes they are held in `pendingURL`.

| URL | resolves to |
|---|---|
| `sword://Bible/John%203:16` | John 3:16 |
| `sword://KJV/Romans%208:28` | Romans 8:28 (module name as host; honoured only for a Bible or a commentary) |
| `sword://StrongsRealGreek/John%203:16` | John 3:16 in the current Bible (a lexicon or unknown host is ignored; `?type=commentary` opens the current commentary) |
| `sword://Bible/Jude` | Jude 1:1 |
| `sword://Bible/1John` | 1 John 1:1 (a bare book in any spelling, unspaced numbered ones included) |
| `sword://Bible/Genesis%201:1.` | Genesis 1:1 (trailing period tolerated) |
| `sword://Bible/John%203:0` | John 3:1 |

The verse is read by `URLRouter`, not the parser: its leading ASCII digits, and at least 1 — a `0` in the verse-position key is a restore the reader ignores, so `:0`, `:-5` and `:abc` open at verse 1. A verse past the end of the chapter is passed through. An unresolvable ref is ignored (no navigation, no history, one `alog` line).
